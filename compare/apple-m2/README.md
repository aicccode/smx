# Apple M2：改造前后与 OpenSSL、BouncyCastle 的性能对比

本目录记录 2026-11-06 在一台空闲 Mac 上做的对比：八种语言**改造前**（`3397c6d`）和**改造后**（`a327a78`）各测一遍，同时测 OpenSSL 3.0.13、OpenSSL 3.6.5 和 BouncyCastle 1.86。x86 上的对比见 [上一级目录](../README.md)。

## 测试环境与方法

- **机器：** Apple M2（4 个性能核 + 4 个能效核），8 GB 内存，macOS 14.1.1，接交流电，测试期间没有其他负载。所有程序依次运行，不并行；整个过程在 `caffeinate` 下进行，每个程序启动前等待 10 秒冷却。`results-2026-11-06/state.log` 记录了每次启动前的负载和温控状态。
- **计时：** 每项操作先预热，再采 7 个样本，每个样本至少 200 ms，取中位数。每种实现完整运行 3 轮，表中是 3 轮中位数的中位数。各实现 3 轮之间差异的中位数在 0% 到 3.3% 之间。
- **同一套测试程序测前后两个版本：** 每种语言只有一份测试程序，分别链接改造前和改造后的代码，只调用两边都有的接口。计时前先做正确性检查，例如签名能通过验签、改动消息后验签失败、加解密能还原、密钥交换双方结果一致且确认值通过。任何一项不通过，程序就会退出。
- **操作：** SM3 对 64 B、1 KiB、1 MiB 输入求哈希；SM4 为 CBC + PKCS#7；SM2 签名使用默认用户 ID，加解密的明文为 32 字节；密钥交换包含双方的全部计算和确认值校验。
- **编译器与运行时：** Apple clang 15.0.0（`-O3`）、rustc 1.94.1（release）、Go 1.25.14、.NET 8.0.427、JBR 17.0.11（Java 和 BouncyCastle 共用）、Node.js 22.23.4、Python 3.9.6（系统自带）、Swift 5.10（`-O -wmo`）。
- **OpenSSL：** 从官方源码包编译，下载后核对过 SHA-256。配置为 `./Configure darwin64-arm64-cc no-shared no-tests`，测试程序静态链接 `libcrypto.a`，通过 `EVP` 接口调用。OpenSSL 不提供 SM2 密钥交换。
- **BouncyCastle：** `bcprov-jdk18on-1.86`，使用轻量级 API，不经过 JCA。密钥交换使用 `SM2KeyExchange`，并带确认值。

## 结论

**和 OpenSSL 3.6.5 比**

- **SM2：** OpenSSL 3.6.5 在 ARM 上比 3.0.13 快很多，签名从 162 µs 降到 55 µs。即便如此，Rust、Go、Swift 的签名仍快 1.4 到 1.7 倍，密钥生成快约 2 倍，加解密快 1.1 到 1.6 倍；Go、Swift 的验签快约 2 倍。C、C# 的签名略快于它，但 C# 的验签和加解密较慢，Java 和 JavaScript 各项都较慢。
- **SM3：** Rust、C#、Swift 略快，JavaScript 持平，C、Go 慢 9% 到 12%。
- **SM4：** OpenSSL 的加密约为 122 MB/s，本库最快的 C 和 Rust 约 60 MB/s。解密方面，Rust 是 OpenSSL 的 6 倍，C 是 1.4 倍，其余语言都比它慢。原因已在 OpenSSL 3.6.5 源码中核实（`include/crypto/sm4_platform.h` 和 `crypto/armcap.c`）：在 ARM 上，OpenSSL 只在三种情况下使用汇编实现——CPU 有 SM4 扩展指令，或者是 Neoverse N1/V1，或者是鲲鹏 920。M2 不属于其中任何一种，所以 OpenSSL 使用 `crypto/sm4/sm4.c` 中的通用 C 实现，它对秘密数据查 4 张 1 KiB 的表，存在缓存时序风险。本库在 SM4 中不使用依赖秘密数据的查表。

**改造前后**

- **SM2：** 所有语言、所有操作都明显变快。签名提速 8 倍（Python）到 228 倍（JavaScript），密钥交换提速 2.2 倍到 128 倍。
- **SM3：** 所有语言提速 1.3 到 4.3 倍。
- **SM4 有倒退：** Go、C#、Java、Python 在 M2 上的加密只有改造前的 26% 到 66%，C 为 83%。C#、Java 的解密也变慢了。改造前这些实现使用查表，有缓存时序风险。改造后，Go 和 C# 在 x86 上使用 AES-NI 或 GFNI，在 ARM 上还没有对应实现；Java 和 Python 无法直接使用这些指令，在所有平台上都用布尔电路 S 盒。这是为常数时间付出的代价。Go 和 C# 补上 ARM 的 AES 实现，是今后优化的方向。Rust 和 C 已经在 ARM 上使用 AES 指令，解密分别达到 839 MB/s 和 195 MB/s。
- **SM4 密钥扩展：** 多数语言变慢，原因同上，每次 0.2 到 1 µs，只在频繁更换密钥时才有影响。Python 为 147 µs。

**和 BouncyCastle 比：** Java 的 SM2 签名快 7.5 倍，加解密快约 9 倍，密钥交换快 13 倍；SM3 两者持平；SM4 只有 BouncyCastle 的约三分之一。BouncyCastle 的 SM4 同样使用查表实现。

**需要说明的几点**

- 多数语言的接口以十六进制字符串或文本收发数据，改造前后都包含这部分转换，所以前后对比是公平的。与直接处理字节的 OpenSSL、BouncyCastle 相比，这一点对本库略为不利。
- Python 改造后默认启用按密钥缓存（可用 `SMX_DISABLE_KEY_CACHE=1` 关闭）。测试中签名和验签反复使用同一个密钥，因此会受益于缓存。
- Java 和 JavaScript 有几项倍数特别大，原因在于改造前的实现：Java 生成密钥时有一个多余的筛选循环；JavaScript 签名时会多出约 22% 的重试，大数运算也很慢。
- 每种语言测试中的具体调用方式和注意事项，见各自的 `kits/<语言>/NOTES.md`。

## 复现

需要的工具：Xcode 命令行工具、rustup，以及 Go、Node.js、.NET 8 SDK、JDK 17 和自行编译的 OpenSSL。这些工具都可以装在 `~/smx-bench/tools` 这样的独立目录中，不需要改动系统。

```bash
compare/apple-m2/prepare.sh 3397c6d HEAD     # 从 git 填充每个 kits/<语言>/base 和 new
compare/apple-m2/build-kits.sh c rust go csharp java javascript python swift
# OpenSSL：在 kits/openssl 中执行
#   cc -O2 -I$OSSL/include -o ob-<版本> openssl_bench.c $OSSL/lib/libcrypto.a
# BouncyCastle：把 bcprov-jdk18on-1.86.jar 放到 kits/bc 中，然后执行
#   javac -cp bcprov-jdk18on-1.86.jar -d cls BcMacBench.java
caffeinate -dimsu compare/apple-m2/run-all.sh          # 约 2 小时，结果写入 results/
python3 compare/apple-m2/table.py compare/apple-m2/results            # 完整表格
python3 compare/apple-m2/table.py compare/apple-m2/results --summary  # 顶层 README 中的汇总表
python3 compare/apple-m2/summarize.py compare/apple-m2/results        # 原始中位数和各轮差异
```

`run-all.sh` 可以通过 `ROUNDS`、`COOLDOWN`、`LANGS`、`OPENSSL_VERSIONS`、`SKIP_BC`、`TOOLS`、`JAVA_HOME` 调整。原始输出放在 `results-2026-11-06/` 中：`*.txt` 每行为“操作、中位数 µs、最小值 µs”，`*.err` 包含版本信息和正确性检查的输出。
